1. Техническое задание

Проблема, назначение и границы

  • Угроза: Сторонний сайт инициирует изменяющий запрос, браузер автоматически прикладывает cookie аутентифицированного пользователя.
  • Назначение: Централизованно подтверждать подлинность POST, PUT, PATCH и DELETE на серверной и браузерной сторонах.
  • Область применения: Веб-приложения с cookie-аутентификацией (формы, переводы, изменение учётных данных).
Цель: Исключить выполнение операций от имени пользователя без его намерения, снизить зависимость от внимательности разработчика и обеспечить наблюдаемость атак.

Основа паттерна: Библиотека + промежуточный слой; метод синхронизатора токена, дополненный проверкой Origin/Referer.

4. Нефункциональные требования

Входы: HTTP-запрос, данные сессии, конфигурация whitelist.
Выходы: Решение (пропустить/403), токен, журнал, метрики.

Производительность системы

  • Полнота: 100% state-changing запросов без токена блокируются.
  • Совместимость: HTTP/1.1-3, TLS 1.2+, REST, HTML/JSON, cookie SameSite.

6. Модель угрозы

Сценарий 1: Поддельный запрос от внешнего сайта

  • Внешняя зона: Вредоносный сайт → Браузер (cookie сессии)
  • Сетевая зона: API Gateway (маршрутизация)
  • Зона приложения: Сервер (CSRF-middleware) → Session Store → Бизнес-БД → Журнал аудита
Риск: Без дополнительного признака намерения сервер считает запрос легитимным и изменяет данные.

Сценарий 2: Ошибочное исключение маршрута

Маршрут ошибочно попадает в whitelist → несанкционированное изменение данных в Бизнес-БД.

7. Механизм защиты

Synchronizer Token Pattern + Origin/Referer

  • F1: Токен ≥ 32 байт, привязан к серверной сессии
  • F2: Middleware проверяет POST/PUT/DELETE/PATCH → 403 при ошибке
  • F5: Проверка Origin/Referer
  • F4: Ротация токена после критичных операций
  • F6/F7: Аудит и метрики

8. Архитектура паттерна

5 микросервисов

  1. CSRF Guard: Реализация F1/F2/F4/F5
  2. Auth & Session: Аутентификация и состояние сессии
  3. Business API: Бизнес-операции приложения
  4. Audit Log: События F6
  5. Metrics: F7 / Prometheus

Жизненный цикл запроса

  1. Проверка метода (POST/PUT/DELETE/PATCH)
  2. Извлечение токена (header/form + cookie)
  3. Проверка источника (Origin/Referer)
  4. Сопоставление токенов
  5. Решение: allow → API или 403
Итог: Невалидный запрос завершается до бизнес-логики; валидный запрос, аудит и ротация токена имеют раздельные контуры.
